# EchoForge 0.5.2

**The in-app updater no longer gets stuck.** A 0.5.0 to 0.5.1 update could sit
at "Downloading - 0%" forever: no connection, no bytes, no error, and no way out
of the pane except quitting. This release fixes that, gives the progress bar
real numbers to show, and adds the two buttons that were missing when something
does go wrong. Everything else in 0.5.1 - transcription, the engines, the
personal terms dictionary, CJK spacing, style rewriting, spoken commands, voice
snippets, the Ask panel, screen queries and the capsule HUD - is unchanged.

This is entirely about **About → Updates**. Nothing about how EchoForge
transcribes, or what it does with your audio, is touched.

## The progress bar now moves

The percentage was not merely inaccurate, it was structurally stuck at 0%:
`URLSession` delivers its progress callbacks only to a session's own delegate,
never to one handed to `download(from:delegate:)` - measured at zero callbacks
over four megabytes, against fourteen the other way. The download now owns the
session it runs on, so "Downloading 0.5.2 - 43%" is a real number counting real
bytes toward a 222 MB update.

## A stalled download is now detected and ended

The original wedge had a cause: the download ran on a shared session whose
resource timeout is **seven days**, and nothing else was watching. A connection
that died silently mid-transfer therefore produced no error to show and no
failure to recover from.

Two things changed:

- The download runs on its own configured session, with an explicit **30-minute
  resource timeout** and a 60-second per-request timeout, instead of inheriting
  the seven-day one.
- A **stall watchdog** ends a transfer that has delivered **nothing at all for 30
  seconds**.

The watchdog measures **silence, not speed**. A slow link is a perfectly normal
way to take a 222 MB update and must be allowed to finish, so there is no rate
floor and no cap on how long a download that is still moving may take. Only a
transfer that has gone completely quiet is refused.

The *check* for updates is a different case and deliberately unchanged: it is one
small request that carries its own 20-second timeout, so it cannot wedge the same
way.

## Cancel, and Retry

- **Cancel** is available while a download is in flight, and puts the pane back
  to the offer rather than into an error.
- A failure - a stall, a dropped connection, a rejected download - now keeps the
  release it was for, so the pane offers **Retry** and one press starts the same
  download again. Previously a failure was a dead end that needed a fresh check.

## Verifying is its own state

After the last byte arrives, EchoForge opens the disk image and checks the
downloaded app's identifier, version and signature. That takes a few seconds, and
a full progress bar left sitting on screen while it happens looks exactly like
the stall this release fixes. So the pane now says **"Verifying 0.5.2…"** with an
indeterminate spinner. Nothing about what is verified changed - the update is
still refused outright if the disk image, the bundle identifier, the version or
the signature is not what was expected, and there is still no "install anyway".

## What has not changed

**EchoForge still never checks for updates on its own.** There is no launch-time
check, no background check and nothing phoning home. Checking, downloading and
installing remain three separate things you press, exactly as before.

Transcription is unchanged and still runs entirely on this Mac. So do style
rewriting, the Ask panel and screen queries, on Apple's on-device model. No audio,
transcript, screenshot or text leaves your computer in this release or any other.

## Upgrading

If you are on 0.5.1 this is a small, safe upgrade with no behaviour changes
outside the updater. If your 0.5.1 install is the one currently stuck at 0%,
quit and reopen EchoForge, then check again - or just install this build by hand
from the DMG below.

This build is produced by `Scripts/build_release.sh` and was published only after
`Scripts/verify_release_package.sh` checked every embedded library's signature and
`@rpath` dependency and **started the app**.

## Installing this build

This release is **not signed with an Apple Developer ID and not notarized**, so
macOS will refuse to open it on the first try - typically "the app is damaged and
can't be opened", or "Apple could not verify EchoForge is free of malware".
Nothing is wrong with the download; macOS simply cannot check who built it.

1. Open `EchoForge.dmg` and drag `EchoForge.app` into `Applications`.
   Do not run it from the mounted disk image.
2. Then do **one** of the following, once:
   - Right-click (or Control-click) the app in `Applications`, choose **Open**, and
     click **Open** in the dialog; or
   - run `xattr -d com.apple.quarantine /Applications/EchoForge.app` in Terminal
     (adjust the path if you installed it elsewhere).

Replacing an existing install keeps your recordings, personal terms, snippets and
downloaded models. Because these builds are unsigned, macOS treats each one as a
new app for permission purposes, so it will ask for Microphone and Accessibility
again - and if a stale **EchoForge** entry is already listed under **Privacy &
Security → Accessibility**, remove it with the minus button and add the new app
back.

This build ships with SenseVoice-Small on board, so it can dictate as soon as it
is installed.

Full instructions, including how to use the Chinese engines and the basics of
recording:
[docs/install.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/install.md).
