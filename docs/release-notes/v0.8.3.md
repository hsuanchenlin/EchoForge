# EchoForge 0.8.3

**Three changes, and none of them touches how audio is recognized.** Chinese
dictation is now written in one script rather than whichever one the model
happened to return; one spoken command can open the newest video from a channel
you listed yourself; and the Settings tab bar draws its keyboard focus ring
around the tab that is actually selected. Recordings, personal terms, snippets,
styles, shortcuts and downloaded models are untouched by this update.

## Chinese transcripts are written in one script, Traditional by default

Speech carries no script. "我們開會" and "我们开会" are the same sentence said out
loud, so which one comes back is a property of the recognizer's training data
rather than of the speaker: **Paraformer** and **SenseVoice** were trained on
Simplified corpora and answer Simplified for a speaker of Taiwanese Mandarin
every time, and **Whisper** mixes the two inside a single sentence
(`這個项目的进度很好` is a real shape of its output). Someone who writes
Traditional was correcting every dictation by hand, and no engine setting could
fix it, because the script is not an input any engine takes.

EchoForge now decides it instead. **Settings → Transcription → Chinese Output
Script** is `Traditional` by default and `Simplified` if you pick it, and every
Chinese transcript is written in the one you chose, from every engine. An
install that predates the setting reads as Traditional, exactly as a fresh one
does.

There is deliberately no third "leave it alone" value. What the recognizer
returns is not a choice anybody made and is not stable from one dictation to the
next, so "leave it alone" would mean "let the model decide, differently each
time", which is the behaviour this setting exists to end.

**It applies only after Chinese recognition, and it is an output setting only.**
It never makes recognition Chinese, never moves your dictation language and
never tilts auto-detect. It converts only text that both the dictation language
and the characters agree is Chinese, so:

- **English dictation stays English**, including on a Mac whose dictation
  language is set to Chinese. A mostly-Latin transcript is not a Chinese
  transcript and nothing in it is touched.
- **Japanese and Korean are never touched.** Kanji and hanja are Han characters
  too, and `学 → 學` in a Japanese transcript is a corruption rather than a
  normalization, so those languages close the conversion off entirely.
- **Latin words, digits, emoji, punctuation of both widths, whitespace and
  Whisper timestamps come out exactly as they went in.** The mapping is macOS's
  own ICU `Hans-Hant` / `Hant-Hans` transform applied one character at a time
  and refused unless it hands back exactly one character, so this is a property
  of the code rather than a promise. No model, no network, no prompt, no
  hand-maintained character table.

It converts the recognizer's words and never yours. It runs before the personal
terms dictionary, so a dictionary entry is written out in the script you typed
it in and still matches either way, and a voice snippet template is inserted
byte for byte.

The stages after it agree with it rather than fighting it. Style rewriting is
asked for its instruction in the transcript's own script and its guard refuses a
rewrite that switched script, so the model cannot undo your choice. A spoken
"翻譯成簡體中文" is still answered in Simplified even if you write Traditional,
because a spoken request outranks a setting, while a bare "translate to Chinese"
follows the setting. Spoken commands are read off the converted transcript, so
every Chinese spelling the grammar accepts is listed in both scripts.

**Nothing already in History is rewritten.** Normalization is part of
transcribing, so it applies to the next dictation and to nothing before it;
`Compare` in History still shows what the engine actually returned.

[docs/chinese-script.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/chinese-script.md)
is the whole story.

## "Open the latest YouTube video from …"

Say **"open the latest YouTube video from Veritasium"** and EchoForge opens that
channel's newest video in a new Chrome tab. The Chinese forms work too
("打開YouTube最新影片…", "打开…最新视频", "播放…", "開啟…", with or without
spaces).

**The allowlist is the security model, and it is the whole of it.** A channel is
named by the canonical `UC…` id you paste into **Settings → Dictionary &
Snippets → YouTube Channels** yourself. Nothing resolves a `@handle`, nothing
searches YouTube, and nothing turns spoken words into a URL, so **no spoken name
can reach a channel that is not on your list**. A name that is not there, or one
that two of your rows answer to, opens nothing and tells you why.

What leaves the app is one request to YouTube's documented channel feed and one
validated video URL handed to Chrome by `NSWorkspace`, which is the same thing
clicking a link does. There is **no scraping, no browser automation, no login,
no cookies, no injected script, no shell and no AppleScript**, and no tab you
already had open is read, closed, reordered or navigated. The feed parser
refuses a document that declares XML entities outright rather than trying to
parse it safely, is bounded in size and entry count, and repairs nothing: an
entry whose link is not a valid YouTube video URL is dropped rather than rebuilt
from the video id beside it.

Two limits worth knowing before you turn it on:

- **Chrome is the browser.** It is the only application this command opens, and
  if Chrome is not installed the command says so and opens nothing.
- **Autoplay is Chrome's decision, not this app's.** Whether the video starts on
  its own, and whether it starts muted, is Chrome's autoplay policy and
  YouTube's. Nothing here tries to influence either, and the Settings pane says
  so.

It rides on spoken commands, which are **off by default**
(`Settings → Shortcuts → Ask & Spoken Commands → Spoken commands`), and has its
own switch beside the channel list. It is the one spoken command that does not
fall back to dictation once its marker matches: every spelling names YouTube and
says which video is wanted, so a transcript that begins with it was not a
sentence anyone was writing. The recording is kept in History either way.

[docs/youtube-latest-video.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/youtube-latest-video.md)
is the whole story, including how to find a channel id.

## The Settings focus ring is on the tab that is selected

0.8.2 widened the Settings sheet so its eight tab titles stopped being truncated,
and said that also settled the keyboard focus ring. Measured afterwards, that
second half was wrong: on macOS 26, AppKit's `NSSegmentedControl` drew the focus
ring about 6 pt wider than the blue selection pill, on every tab, at the old
550 pt and at the new 680 pt alike. Widening the sheet could not fix it and
neither could containing the panes, because both rectangles are produced inside
AppKit.

EchoForge now draws that bar itself. The selection fill, the focus frame and the
hit target are all derived from one frame per tab, so they cannot disagree, and
the bar is still one stop in the keyboard loop with the arrow keys moving the
selection and stopping at the ends. The tests read the two rectangles back out
of rendered pixels, so a future drift fails a test rather than shipping.

Two smaller things came with it. A pane can no longer change the width of the
tab bar as you switch tabs, which it previously could. And only the tab you are
looking at is built, so a pane you never open, such as **Cloud**, is now never
constructed at all rather than built and hidden. Nothing about your keychain
changes: the Cloud pane has only ever read a stored API key when you actually
open it, and that is still true.

The v0.8.2 notes now carry that correction inline.

## Everything else is unchanged from 0.8.2

- **The cloud path is still opt-in and still off.** Two features can be pointed
  at an OpenAI-compatible provider, speech transcription and the spoken
  "Translate to …" command, and switching either takes an explicit acceptance of
  a sheet naming what is uploaded and where. Style rewriting, the Ask panel
  (⌥A) and screen questions (⌥S) have no cloud path at all, enforced in code.
  A 0.8.3 install you never point at a provider sends nothing, anywhere, with
  the single exception of the YouTube command above if you turn it on and use
  it: that request carries a channel id you typed and nothing about you.
  [docs/cloud-api.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/cloud-api.md).
  If you need "not present" rather than "not enabled",
  `Scripts/build_release.sh --offline-only` still builds exactly that; it is not
  published as a separate download here.
- **The app is still thin.** It ships no model weights. The model you choose is
  fetched on demand and checksummed, SenseVoiceSmall as a verified model pack
  and every other engine by its own downloader, and lands in Application
  Support, where it survives replacing the app. This build does not change the
  SenseVoiceSmall pack, so an engine you have already downloaded is not fetched
  again.
  [docs/model-packs.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/model-packs.md).
- **The ⌥M engine shortcut is as it was**, including the pill drawn on every
  attached display and the VoiceOver announcement, and **Settings → Model**
  still opens with the line naming the binding actually in force.
- **EchoForge still never checks for updates on its own.** Checking,
  downloading and installing remain three separate things you press.

## Installing this build

This release is **not signed with an Apple Developer ID and not notarized**, so
macOS will refuse to open it on the first try, typically "the app is damaged and
can't be opened", or "Apple could not verify EchoForge is free of malware".
Nothing is wrong with the download; macOS simply cannot check who built it.

1. Open `EchoForge.dmg` and drag `EchoForge.app` into `Applications`.
   Do not run it from the mounted disk image.
2. Then do **one** of the following, once:
   - Right-click (or Control-click) the app in `Applications`, choose **Open**,
     and click **Open** in the dialog; or
   - run `xattr -d com.apple.quarantine /Applications/EchoForge.app` in Terminal
     (adjust the path if you installed it elsewhere).

### Expect to grant permissions again

Because these builds are unsigned, macOS treats each one as a **new
application** for privacy purposes. After you replace your copy, it will ask
again for **Microphone** and **Accessibility**, and for **Screen Recording** the
first time you use ⌥S. **This is expected and is not a regression**; it happens
on every unsigned update and will keep happening until these builds are signed
with a Developer ID.

If a stale **EchoForge** entry is already listed under **System Settings →
Privacy & Security → Accessibility**, remove it with the minus button and add
the new app back; macOS otherwise keeps showing the old entry as granted while
the new build has nothing.

The same reason produces one more prompt, and only for people who have stored a
cloud API key: the first time the updated app reads it, macOS asks "EchoForge
wants to use information stored in your keychain". Choose **Always Allow** and
it stops asking. An install that has never turned the cloud path on never reads
the Keychain at all.

Replacing an existing install keeps your recordings, personal terms, snippets,
styles and downloaded models.

Full instructions, including how to use the Chinese engines and the basics of
recording:
[docs/install.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/install.md).

Produced by `Scripts/build_release.sh` and published only after
