# EchoForge 0.8.5

**One change: the ⌥Y command key now understands the sentence that names the
channel, not only the one that names the video.** Nothing about recognition,
transcripts, styles, storage or the security model changes in this build, and
recordings, personal terms, snippets, styles, shortcuts and downloaded models
are untouched by this update.

## "Open YouTube channel Valley 101" is the same command

Hold **⌥Y**, say a channel's name, let go, and that channel's newest video opens
in a new Chrome tab. The name on its own has been the whole command since 0.8.4,
and a full sentence is accepted and stripped in front of it - but until now the
only sentences the grammar knew were the ones naming the **video**: "open the
latest YouTube video from …", "打開YouTube最新影片…".

Naming the **channel** is at least as natural a way to ask for the same thing,
and it failed in the way that is hardest to act on. With no marker recognized,
the whole sentence becomes the spoken channel name, so "open YouTube channel
Valley 101" asked the list for a row called *"open youtube channel valley 101"*,
found none, and answered **"Channel not in your list"** - pointing at the one
thing that was already correct. It took four attempts against a channel that had
been configured all along.

Both families are now listed, in English and in both Chinese scripts:

| Said into ⌥Y | Opens |
| --- | --- |
| `Valley 101` | the newest video from that channel |
| `Open the latest YouTube video from Valley 101` (also `newest`, `play`, `open latest`) | the same |
| `Open YouTube channel Valley 101` (also `play`, and with or without `the`) | the same |
| `打開YouTube最新影片科技島讀` (also `打开…最新视频`, `播放…`, `開啟…`) | the same |
| `打開YouTube頻道科技島讀` (also `打开…频道`, `播放…`, `開啟…`) | the same |

Spacing still does not have to match, behind either family: a channel stored as
`valley101` answers to "valley 101", and one stored as `小Lin說` answers to
"小 Lin 說". The Chinese spellings are listed in both scripts, so 頻道 stands
beside 频道 the way every CJK spelling in this grammar does.

**Settings → Dictionary & Snippets → YouTube Channels** now teaches both
wordings in its usage line, since a pane showing only one is exactly how an
unsupported phrasing looks like a missing channel.

### Widening the sentence does not widen what can be opened

**The allowlist is still the whole security model, and it is unchanged.** What
follows the marker still has to equal one channel you stored, in full, through
the same two deterministic tiers - the stored spelling, then the same comparison
with internal spaces folded away - with ambiguity detected in each tier
separately and separately refused. Nothing is stemmed, truncated or partially
matched, so "open YouTube channel Valley", a misheard "open YouTube channel Bali
101", and any name that is not on your list still reach **nothing** and say so.

A channel is still named only by the canonical `UC…` id you paste into Settings
yourself: nothing resolves a `@handle`, nothing searches YouTube, and no spoken
words are turned into an address.

### Your dictation shortcut is still text and only text

This grammar has exactly one caller - the ⌥Y command key - and that has not
changed. The router that reads dictations has no case that opens anything, so
**no wording of a dictation can reach a browser**, including the new ones:
saying "open YouTube channel Valley 101" into your dictation key **types those
words**. And what ⌥Y captured is still read only as a channel name - it never
reaches style rewriting, the Ask panel, the snippet expander or the translator,
and has no path back into the document you were typing in. The tests assert both
over the new wordings.

What leaves the app is unchanged from 0.8.4: one request to YouTube's documented
channel feed and one validated video URL handed to Chrome by `NSWorkspace`.
There is **no scraping, no browser automation, no login, no cookies, no injected
script, no shell and no AppleScript**, and no tab you already had open is read,
closed, reordered or navigated. Autoplay remains Chrome's decision and YouTube's,
not this app's, and Chrome remains the only application this command opens.

[docs/youtube-latest-video.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/youtube-latest-video.md)
is the whole story, including how to find a channel id.

## Everything else is unchanged from 0.8.4

- **The ⌥Y key, its Settings pane and its defaults are as they were.** The key
  is bound in **Settings → Shortcuts → YouTube Command**, alongside ⌥` (record),
  ⌥A (Ask), ⌥S (ask about the screen) and ⌥M (switch engine). The optional
  on-device name matcher is still **off by default**, still a chooser rather
  than a resolver that can only return a channel already on your list, still
  fails closed, still never leaves this Mac, and still says so when it is used.
- **Chinese transcripts are still written in one script**, Traditional unless
  you picked Simplified, as an output setting only: it never makes recognition
  Chinese, never moves your dictation language and never touches Japanese or
  Korean.
  [docs/chinese-script.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/chinese-script.md).
- **The cloud path is still opt-in and still off.** Two features can be pointed
  at an OpenAI-compatible provider, speech transcription and the spoken
  "Translate to …" command, and switching either takes an explicit acceptance of
  a sheet naming what is uploaded and where. Style rewriting, the Ask panel
  (⌥A), screen questions (⌥S) and the channel matching above have no cloud path
  at all, enforced in code. A 0.8.5 install you never point at a provider sends
  nothing, anywhere, with the single exception of the YouTube command if you add
  a channel and use it: that request carries a channel id you typed and nothing
  about you.
  [docs/cloud-api.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/cloud-api.md).
  If you need "not present" rather than "not enabled",
  `Scripts/build_release.sh --offline-only` still builds exactly that; it is not
  published as a separate download here.
- **The app is still thin.** It ships no model weights. The model you choose is
  fetched on demand and checksummed, SenseVoiceSmall as a verified model pack
  and every other engine by its own downloader, and lands in Application
  Support, where it survives replacing the app. This build does not change the
  SenseVoiceSmall pack, so an engine you have already downloaded is not fetched
  again.
  [docs/model-packs.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/model-packs.md).
- **EchoForge still never checks for updates on its own.** Checking,
  downloading and installing remain three separate things you press.

## Installing this build

This release is **not signed with an Apple Developer ID and not notarized**, so
macOS will refuse to open it on the first try, typically "the app is damaged and
can't be opened", or "Apple could not verify EchoForge is free of malware".
Nothing is wrong with the download; macOS simply cannot check who built it.

1. Open `EchoForge.dmg` and drag `EchoForge.app` into `Applications`.
   Do not run it from the mounted disk image.
2. Then do **one** of the following, once:
   - Right-click (or Control-click) the app in `Applications`, choose **Open**,
     and click **Open** in the dialog; or
   - run `xattr -d com.apple.quarantine /Applications/EchoForge.app` in Terminal
     (adjust the path if you installed it elsewhere).

### Expect to grant permissions again

Because these builds are unsigned, macOS treats each one as a **new
application** for privacy purposes. After you replace your copy, it will ask
again for **Microphone** and **Accessibility**, and for **Screen Recording** the
first time you use ⌥S. **This is expected and is not a regression**; it happens
on every unsigned update and will keep happening until these builds are signed
with a Developer ID.

If a stale **EchoForge** entry is already listed under **System Settings →
Privacy & Security → Accessibility**, remove it with the minus button and add
the new app back; macOS otherwise keeps showing the old entry as granted while
the new build has nothing.

The same reason produces one more prompt, and only for people who have stored a
cloud API key: the first time the updated app reads it, macOS asks "EchoForge
wants to use information stored in your keychain". Choose **Always Allow** and
it stops asking. An install that has never turned the cloud path on never reads
the Keychain at all.

Replacing an existing install keeps your recordings, personal terms, snippets,
styles and downloaded models.

Full instructions, including how to use the Chinese engines and the basics of
recording:
[docs/install.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/install.md).

## How this build was made

Produced by `Scripts/build_release.sh` and published only after
`Scripts/verify_release_package.sh` checked every embedded library's signature
and `@rpath` dependency and **started the app**.
