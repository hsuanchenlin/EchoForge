# EchoForge 0.8.2

**Two defects with one surface between them: Settings is a sheet.** Its tab bar
had outgrown the window and every title was truncated, and leaving it open was
enough to cancel a restart of your Mac. This release is those two fixes and
nothing else - no engine, model, transcription or privacy behaviour changed.

## The Settings tab bar fits again

Settings opened at 550 pt, a width chosen when it had four tabs and never
revisited as tabs were added. macOS draws a SwiftUI `TabView` inside a sheet as
a single `NSSegmentedControl` whose intrinsic width is the sum of its titles, so
by eight tabs the bar wanted 637 pt and had 518: **Model**, **Style**, **Cloud**
and **About** all rendered as `Mo…`, `St…`, `Cl…`, `Ab…`.

The sheet is now 680 pt, which leaves the bar 648 pt and 11 pt of slack, and
every title is drawn in full.

Truncation was the visible half. The other half is that a *compressed*
segmented control sizes its segments from the whole layout, including the
content of the pane currently on screen, so each segment's rectangle shifted as
you changed tabs - which is how the keyboard focus ring came to be drawn around
a different rectangle than the blue selection pill. At the uncompressed width
the bar sits at its intrinsic size and every segment is where it looks like it
is, so keyboard navigation and the mouse agree.

> **Correction, measured after this release:** the second half of that claim is
> wrong. Even uncompressed, the bar's layout still follows the displayed pane -
> at 680 pt a 900 pt pane lays it out 657 pt instead of 648 - so this release
> fixed the truncation and only that. Pane widths are since contained by
> `settingsPane()` (`SettingsSheetLayout.swift`), and whether the focus ring and
> the selection pill actually agree is still unverified pending an interactive
> check on a real Mac.

The width is now measured rather than guessed: `SettingsTabBarFitTests` lays out
a real `NSSegmentedControl` from the shipped tab titles and fails the build if
they stop fitting, or come within 4 pt of not fitting. Adding a tab or
lengthening a title now says so at test time instead of shipping.

## An open Settings sheet no longer cancels your restart

If Settings was open when you chose **Restart** or **Shut Down**, macOS put up
***"'EchoForge' interrupted restart"*** and stopped there. Nothing was wrong
with the app: AppKit refuses the quit Apple Event that loginwindow sends while a
window-modal sheet is visible, so EchoForge answered "no" on your behalf and the
restart you asked for did not happen.

EchoForge now listens for `NSWorkspace.willPowerOffNotification` - the warning
macOS sends before it starts asking apps to quit - and takes its own sheets and
confirmation dialogs down first, so the quit event arrives with nothing in its
way. Every `.sheet` and `.confirmationDialog` in the app is covered, and a
source scan in the test suite fails if a new one ships without it.

You do not lose anything you were doing: preferences are written as you change
them, so a sheet dismissed this way has already saved.

Two obvious-looking fixes were tried, measured, and are deliberately **not**
what is shipped, because neither works: AppKit's sheet check runs *before*
`applicationShouldTerminate`, so the app delegate is never consulted at all, and
`NSWindow.endSheet` closes the AppKit sheet without touching the SwiftUI state
that presents it, so SwiftUI puts it straight back. Only writing the SwiftUI
binding actually dismisses a SwiftUI sheet.

## Everything else is unchanged from 0.8.1

- **The ⌥M engine shortcut is exactly as it was in 0.8.1**, including the pill
  drawn on every attached display and the VoiceOver announcement, and
  **Settings → Model** still opens with the line naming the binding actually in
  force.
- **The cloud path is still opt-in and still off.** Two features can be pointed
  at an OpenAI-compatible provider - speech transcription and the spoken
  "Translate to …" command - and switching either takes an explicit acceptance
  of a sheet naming what is uploaded and where. Style rewriting, the Ask panel
  (⌥A) and screen questions (⌥S) have no cloud path at all, enforced in code.
  A 0.8.2 install you never point at a provider sends nothing, anywhere.
  [docs/cloud-api.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/cloud-api.md).
  If you need "not present" rather than "not enabled",
  `Scripts/build_release.sh --offline-only` still builds exactly that; it is not
  published as a separate download here.
- **The app is still thin.** It ships no model weights. The model you choose is
  fetched on demand and checksummed - SenseVoiceSmall as a verified model pack,
  every other engine by its own downloader - and lands in Application Support,
  where it survives replacing the app. The SenseVoiceSmall pack is published
  once under its own tag rather than per app release, and this build does not
  change it, so an engine you have already downloaded is not fetched again.
  [docs/model-packs.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/model-packs.md).
- **EchoForge still never checks for updates on its own.** Checking,
  downloading and installing remain three separate things you press.
- Recordings, personal terms, snippets, styles, shortcuts and downloaded models
  are untouched by this update.

## Installing this build

This release is **not signed with an Apple Developer ID and not notarized**, so
macOS will refuse to open it on the first try - typically "the app is damaged
and can't be opened", or "Apple could not verify EchoForge is free of malware".
Nothing is wrong with the download; macOS simply cannot check who built it.

1. Open `EchoForge.dmg` and drag `EchoForge.app` into `Applications`.
   Do not run it from the mounted disk image.
2. Then do **one** of the following, once:
   - Right-click (or Control-click) the app in `Applications`, choose **Open**,
     and click **Open** in the dialog; or
   - run `xattr -d com.apple.quarantine /Applications/EchoForge.app` in Terminal
     (adjust the path if you installed it elsewhere).

### Expect to grant permissions again

Because these builds are unsigned, macOS treats each one as a **new
application** for privacy purposes. After you replace your copy, it will ask
again for **Microphone** and **Accessibility**, and for **Screen Recording** the
first time you use ⌥S. **This is expected and is not a regression** - it happens
on every unsigned update and will keep happening until these builds are signed
with a Developer ID.

If a stale **EchoForge** entry is already listed under **System Settings →
Privacy & Security → Accessibility**, remove it with the minus button and add
the new app back; macOS otherwise keeps showing the old entry as granted while
the new build has nothing.

The same reason produces one more prompt, and only for people who have stored a
cloud API key: the first time the updated app reads it, macOS asks "EchoForge
wants to use information stored in your keychain". Choose **Always Allow** and
it stops asking. An install that has never turned the cloud path on never reads
the Keychain at all.

Replacing an existing install keeps your recordings, personal terms, snippets,
styles and downloaded models.

Full instructions, including how to use the Chinese engines and the basics of
recording:
[docs/install.md](https://github.com/hsuanchenlin/EchoForge/blob/master/docs/install.md).

## How this build was made

Produced by `Scripts/build_release.sh` and published only after
`Scripts/verify_release_package.sh` checked every embedded library's signature
and `@rpath` dependency and **started the app**.
